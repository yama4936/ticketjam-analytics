# 収集・判定方針

## 初期運用

- 対象: iLiFE! の公開公演ページ。DBの `groups` で管理する。
- 公演候補を1時間ごとに発見し、最初は最大5公演を観測。候補総数と取込済み数を区別し、全ヒロインズを網羅したとは表示しない。
- 公演と出品は取得元の外部IDで一意。複数グループから見つかった同じ公演も一つに関連づける。
- ホームサーバーの独立Dockerワーカーが毎時0分（Asia/Tokyo）にジョブを登録。起動時も当該時間枠を登録する。
- ジョブを再実行しても、保存済みの時間枠は再保存しない。失敗時は2回まで間隔をあけて再試行。
- 成功した観測から履歴を蓄積。過去の価格・出品日時を補完しない。

## アクセス

- User-Agentでプロジェクトを明示し、HTTP取得のみを行う。
- robots.txtを取得して許可されるパスだけを利用。取得できない場合は収集を進めない。
- PostgreSQLの共有ロックを使い、全ワーカーで最低5秒のリクエスト間隔を共有。robots.txtのCrawl-delayが長ければそれに従う。
- 403・401・認証等へのリダイレクト・検知したアクセス確認画面で、取得元を確認待ちとして停止。公開公演へのリダイレクトは取得失敗と記録し、追従も成約判定もしない。
- 429ではRetry-Afterを尊重し、最低1時間待つ。IP変更、認証回避、CAPTCHA回避はしない。
- 1リクエスト30秒、最大3MB、1公演20ページ上限。ページ上限に達した場合は部分取得とする。
- 取得元の自動再利用許諾について、robots.txtだけで包括的に許可されたとは判断しない。公開前に取得項目・集計の公開範囲を確認する。

## データと判定

- 保存する原文は分析に必要な席種・整理番号欄に限定。説明全文、出品者プロフィール、画像、コメントを公開データとして取り込まない。
- 掲載中の単価と枚数を別項目として保存し、観測履歴を残す。
- 成約の公開表示を安定して識別する処理はまだ未実装。現時点で実データを成約確認扱いにしない。
- 一覧から消えただけの出品は、全ページ取得・件数一致・重複なしがそろった観測でのみ「掲載終了・理由不明」にする。
- 取得不能やHTML構造変化、件数不一致では掲載終了を判定しない。部分取得の観測値は部分取得と明記して保存。
- 成約確認機能のため、最後の掲載確認と成約観測の区間・成約価格専用欄を用意。最終出品価格を成約価格へコピーしない。
- 枚数減少は枚数変更。部分成約と断定しない。新しい出品IDを既存のチケットと自動で同一視しない。
- 整理番号の接頭辞だけで券種を決定しない。指定席・未確定・解析不明を分離する。

## 参照した利用条件

2026-09-30に売買サイトの [利用規約](https://ticketjam.jp/terms) とrobots.txtを確認した。
第27条はサイト・サービスの知的財産権と、サービス外の使用許諾を意味しないことを定めている。
robots.txtの取得可能範囲を、転載や第三者への再配信の許諾と同一視しない。
分析では価格・枚数・日時・番号帯の観測に限定し、元ページへリンクする。記事サイト `/magazine` の規約を売買サイトの規約と取り違えない。
